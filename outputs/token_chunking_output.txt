TASK 1: MEASURING & SIZING BY TOKENS (VS. CHARACTER-BASED SIZING)
-------------------------------------------------------------------------------------
Why character-based chunking fails: 500 characters of dense technical text or JSON
can explode the token budget, while 500 characters of simple text wastes space.

Dense Sample  (len: 226 chars) -> 86 tokens (Token density: 2.63 chars/tok)
Simple Sample (len: 149 chars) -> 25 tokens (Token density: 5.96 chars/tok)

=> Token-aware chunking enforces true context window boundaries regardless of text density.

TASK 4: JUSTIFICATION OF CHOSEN TOKEN SIZE AND OVERLAP
-------------------------------------------------------------------------------------
Target RAG Architecture:
  • Embedding Model : OpenAI text-embedding-3-small (8,191 max tokens)
  • Generation Model: OpenAI GPT-4o-mini / GPT-3.5-Turbo (16K - 128K context window)

1. Token Size Justification (400 Tokens):
   • Semantic Granularity: 400 tokens (~300 words / 2-3 paragraphs) captures a complete,
     standalone sub-topic (e.g., full refund criteria, escalation flowchart) without dilution.
   • Context Window Math (Top-k = 4):
       - System Prompt & Instructions : ~250 tokens
       - User Query & History         : ~200 tokens
       - 4 Retrieved Chunks (4 × 400) : 1,600 tokens
       - Output Generation Budget     : ~500 tokens
       --------------------------------------------------
       - Total Query Context Footprint : ~2,550 tokens (fits well inside token budgets)

2. Overlap Justification (60 Tokens / 15%):
   • Preserves Average English Sentence: The average English sentence in documentation is 15-25 words
     (~20-35 tokens). A 60-token overlap guarantees that any sentence cut across a boundary will be
     fully repeated in the following chunk.
   • Cost vs. Context Trade-Off Analysis:
   Overlap  | % of Size  | Chunks  | Stored Toks  | Redundancy   | Cost Trade-off      
   ------------------------------------------------------------------------------
   0        |      0.0% |      2  |        653  | +    0.00%    | Baseline (Risky)
   30       |      7.5% |      2  |        683  | +    4.59%    | Minimal
   60       |     15.0% |      2  |        713  | +    9.19%    | Sweet Spot (Knovera)
   100      |     25.0% |      3  |        806  | +   23.43%    | Excessive Cost
   150      |     37.5% |      3  |        953  | +   45.94%    | Excessive Cost

   Conclusion: 60 tokens (15%) provides the optimal balance: 100% boundary safety with only ~15% storage overhead.
